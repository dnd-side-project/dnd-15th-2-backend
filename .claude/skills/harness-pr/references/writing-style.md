# PR 본문 문체 규칙

PR 제목과 본문을 쓸 때 적용한다. 리뷰어가 읽는 보고 문서이므로 사실과 근거만
남기고 홍보 문구와 AI 특유의 상투적 표현을 제거한다.

## 0. 작성 원칙

- AI 말투·표현·키워드를 쓰지 않는다. 2절의 금지 표현에 더해 작성 도구 이름(Claude, AI 등)과
  `Generated with ...` 같은 서명 줄을 본문에 넣지 않는다.
- 이번 작업에서 한 일과 그 근거 자료를 분명히 적는다. 근거 자료는 테스트 계획, 테스트 보고서,
  실행한 명령과 결과이며 경로나 링크로 연결한다.
- 쓸데없는 말과 문장은 모두 뺀다. 같은 내용을 두 번 쓰지 않고, 표와 짧은 목록으로 나눠 훑어보기
  쉽게 만든다.
- 짧게 쓰되 무엇을 왜 바꿨고 결과가 어떤지가 드러나게 한다.
- 처음 보는 리뷰어가 한 번 읽고 이해할 수 있게 쓴다. 본문은 3,000자 이하를 기준으로 한다.
- 결정 근거, 대안 비교, 커밋별 설명은 `TASK.md`나 보고서에 두고 본문에는 결론과 링크만 둔다.
- 완료 조건 표는 `확인한 것 | 결과` 두 칸으로 쓴다. 검증 방법은 결과 문장에 넣고 증빙은 결과
  칸에 링크로 붙인다.
- 진행한 작업의 흐름이나 구조 변화는 `mermaid` 코드 블록 다이어그램으로 보여 줄 수 있다. 필수는
  아니다.

## 1. 종결 어미는 합쇼체

본문의 모든 서술은 `~합니다`, `~했습니다`, `~입니다`로 끝낸다.

근거: `.github/PULL_REQUEST_TEMPLATE.md`가 합쇼체다("단위 또는 통합 테스트를
실행했습니다", "라벨이 정확히 하나 있습니다"). 템플릿을 채우는 글이 템플릿과
다른 말투면 문서가 어긋난다.

| 쓰지 않는다 | 쓴다 |
| --- | --- |
| 스킬 3종을 추가한다. | 스킬 3종을 추가했습니다. |
| 검증은 통과했다. | 검증은 통과했습니다. |
| 영향은 없다. | 영향은 없습니다. |

예외:

- **PR 제목** — `<type>: <summary>` 형식이다. summary는 저장소 관행상 한글을
  쓴다(예: `feat: 방향 매칭 워커와 원자적 수신자 확정 구현`). 이 종결 어미
  규칙(합쇼체)은 본문에만 적용하고, 제목의 summary는 명사형으로 끝낸다.
- **인용** — 이슈 본문, 로그, 문서를 그대로 인용할 때는 원문 말투를 유지한다.
- **저장소 규범 문서** — `AGENTS.md`, `docs/`, 스킬 문서는 평서체(`~한다`)가
  기준이다. PR 본문과 혼동하지 않는다.

## 2. 쓰지 않는 표현

| 금지 | 이유 | 대신 |
| --- | --- | --- |
| 이모지 전부 (🚀 ✅ 🎉 📝 ⚡) | 리뷰 노이즈이고 검색·diff에서 방해된다 | 텍스트로 쓴다 |
| 과장 형용사 — 완벽한, 강력한, 혁신적인, 매끄러운, 손쉽게, 깔끔하게 | 검증할 수 없는 주장이다 | 무엇이 어떻게 달라졌는지 사실로 쓴다 |
| 근거 없는 정도 부사 — 대폭, 크게, 매우, 상당히, 획기적으로 | 측정값이 없으면 뜻이 없다 | 숫자를 쓰거나 뺀다 |
| 자기 평가 — 훨씬 나아졌습니다, 크게 개선했습니다, 최적화했습니다 | 판단은 리뷰어 몫이다 | 변경 내용과 측정 결과만 쓴다 |
| 인사말·맺음말 — 안녕하세요, 리뷰 부탁드립니다, 감사합니다, 확인 부탁드려요 | PR 본문은 편지가 아니다 | 넣지 않는다 |
| 상투적 도입·마무리 — 이번 PR에서는, 요약하자면, 결론적으로, 핵심은, 앞으로 ~할 것으로 기대됩니다 | 내용 없는 연결어다 | 바로 본론을 쓴다 |
| 번역투 — ~을 통해, ~에 대해서, ~에 있어서, ~라고 할 수 있습니다, ~하는 것이 가능합니다, ~을 진행하였습니다 | 영어 구문을 직역한 어색한 한국어다 | ~로, ~는, ~할 수 있습니다, ~했습니다 |
| 피동 남용 — 되어집니다, 보여집니다, 생각되어집니다 | 이중 피동이고 주체가 흐려진다 | 능동으로 쓴다 |
| 1인칭·감정 — 제가, 저는, 아쉽게도, 다행히, 안타깝게도 | PR은 변경 사실을 적는 문서다 | 주어 없이 사실만 쓴다 |
| 기계적 3항 나열 | 항목 수를 맞추려고 없는 내용을 만든다 | 있는 만큼만 쓴다 |
| 굵은 글씨·불릿 남발 | 전부 강조하면 아무것도 강조되지 않는다 | 문단으로 쓰고 목록은 실제 열거일 때만 |
| 같은 내용 반복 요약 | 도입·본문·결론에 같은 말을 세 번 쓴다 | 한 번만 쓴다 |
| 커밋 해시, 브랜치 이름, CI 실행 ID, 작업 폴더 경로 | 리뷰어에게 뜻이 없고 문장을 끊는다 | 쓰지 않는다. CI 실행은 `[실행 기록](URL)`처럼 한국어 글자에 링크를 건다 |
| 풀어 쓰지 않은 영어 용어 — artifact, concurrency, worktree, synchronize, skipped | 처음 보는 사람이 뜻을 따로 찾아야 한다 | 결과 파일, 앞 실행 취소, 별도 작업 폴더, 새 커밋이 올라올 때, 건너뜀 |
| 코드 서식 남발 | 백틱이 많으면 문장이 끊겨 읽히지 않는다 | 리뷰어가 실행하거나 찾아볼 명령·파일에만 쓴다 |

GitHub 화면에 그대로 보이는 이름(workflow, check 이름)과 리뷰어가 실행할 명령은 원어로 쓰되 한 번만
쓴다.

| 쓰지 않는다 | 쓴다 |
| --- | --- |
| `989f09c`를 revert하면 새 workflow 두 개가 지워집니다. | 문제가 생기면 이 PR을 되돌리면 됩니다. |
| push run 37814129494의 `test` job은 804초였습니다. | 같은 커밋의 두 실행에서 테스트가 796초와 896초 걸렸습니다. [실행 기록](URL) |
| `ci/gh-313-...` worktree에서 hook이 `GIT_DIR`을 물려받습니다. | 별도 작업 폴더에서는 push 전 자동 검사가 저장소를 손상시킬 수 있습니다. |

## 3. 사실과 추측을 구분한다

- 실행한 검증은 명령과 결과를 그대로 적는다.
- 실행하지 않은 검증은 하지 않았다고 적는다. "문제없을 것입니다"로 대체하지
  않는다.
- 추측을 적어야 하면 추측이라고 밝힌다. "영향이 없습니다"와 "Java 소스 변경이
  없어 영향이 없다고 판단했습니다"는 다른 문장이다.
- 리뷰어가 판단해야 할 위험, 미검증 범위, 롤백 절차를 빼지 않는다.

## 4. 초안 제출 전 점검

- [ ] 이모지가 하나도 없는가
- [ ] 모든 서술이 `~습니다`, `~입니다`로 끝나는가
- [ ] 측정값 없이 개선·최적화를 주장하지 않았는가
- [ ] 실행하지 않은 검증을 했다고 쓰지 않았는가
- [ ] 인사말과 맺음말이 없는가
- [ ] 표의 금지 표현이 남아 있지 않은가
- [ ] 작성 도구 이름이나 서명 줄이 없는가
- [ ] 한 일마다 근거 자료(계획·보고서·실행 결과)가 연결됐는가
- [ ] 같은 내용을 두 번 쓰지 않았는가
- [ ] 커밋 해시, 브랜치 이름, CI 실행 ID가 본문에 없는가
- [ ] 영어 용어를 우리말로 풀어 썼는가(GitHub 화면에 보이는 이름과 실행할 명령은 제외)
- [ ] 처음 보는 사람이 한 번 읽고 이해할 수 있는가, 3,000자 이하인가

하나라도 걸리면 고친 뒤에 사용자에게 초안을 보여준다.
