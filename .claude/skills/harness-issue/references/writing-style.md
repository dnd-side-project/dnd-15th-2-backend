# 이슈 본문 문체 규칙

이슈 제목과 본문(목적/범위/완료 조건/백엔드 영향/선행 관계/제외)을 쓸 때
적용한다. 목적은 하나다 — 읽는 사람이 무엇을 왜 하는지, 완료됐을 때 무엇이
검증됐다고 볼 수 있는지 훑어보기만 해도 파악하게 한다.

`harness-pr/references/writing-style.md`(PR 본문 문체 규칙)와 짝을 이루지만
종결 어미가 다르다. 두 문서를 혼동하지 않는다.

## 1. 종결 어미는 평서체

이슈 본문의 모든 서술은 `~한다`, `~했다`, `~이다`로 끝낸다.

근거: 기존 이슈(`#154`, `#163` 등)와 `AGENTS.md`·`docs/`가 전부 평서체다.
합쇼체는 PR 본문에만 적용하는 규칙이다(`harness-pr/references/writing-style.md`
1절).

| 쓰지 않는다 | 쓴다 |
| --- | --- |
| 영향은 없습니다. | 영향은 없다. |
| 재시도 정책을 추가합니다. | 재시도 정책을 추가한다. |
| 기존 필드를 확인했습니다. | 기존 필드를 확인했다. |

예외:

- **이슈 제목** — 명사구로 끝난다. 동사 종결을 쓰지 않는다(예: "신고 접수·
  사유·차단 진입점", "OpenAI 429 Retry-After 처리").
- **완료 조건 체크리스트 항목** — 검증 가능한 조건문이면 되고 종결 어미를
  엄격히 따지지 않는다.
- **인용** — 다른 이슈, 로그, 문서를 그대로 인용할 때는 원문 말투를 유지한다.

## 2. 쓰지 않는 표현

| 금지 | 이유 | 대신 |
| --- | --- | --- |
| 이모지 전부 (🚀 ✅ 🎉 📝 ⚡) | 검색·diff에서 노이즈다 | 텍스트로 쓴다 |
| 과장 형용사 — 완벽한, 강력한, 혁신적인, 매끄러운, 손쉽게, 깔끔하게 | 검증할 수 없는 주장이다 | 무엇이 어떻게 달라지는지 사실로 쓴다 |
| 근거 없는 정도 부사 — 대폭, 크게, 매우, 상당히, 획기적으로 | 측정값이 없으면 뜻이 없다 | 숫자를 쓰거나 뺀다 |
| 자기 평가 — 훨씬 나아진다, 크게 개선한다, 최적화한다 | 판단은 리뷰어·완료 조건 몫이다 | 검증 가능한 완료 조건으로 대체한다 |
| 인사말·맺음말 — 안녕하세요, 확인 부탁드립니다, 감사합니다 | 이슈는 편지가 아니다 | 넣지 않는다 |
| 상투적 도입·마무리 — 이번 이슈에서는, 요약하자면, 결론적으로, 앞으로 ~할 것으로 기대된다 | 내용 없는 연결어다 | 바로 본론을 쓴다 |
| 번역투 — ~을 통해, ~에 대해서, ~에 있어서, ~라고 할 수 있다, ~하는 것이 가능하다, ~을 진행한다 | 영어 구문을 직역한 어색한 한국어다 | ~로, ~는, ~할 수 있다, ~한다 |
| 피동 남용 — 되어진다, 보여진다, 여겨진다 | 이중 피동이고 주체가 흐려진다 | 능동으로 쓴다 |
| 1인칭·감정 — 제가, 저는, 아쉽게도, 다행히 | 이슈는 작업 계약 문서다 | 주어 없이 사실만 쓴다 |
| 기계적 3항 나열 | 항목 수를 맞추려고 없는 내용을 만든다 | 있는 만큼만 쓴다 |
| 굵은 글씨·불릿 남발 | 전부 강조하면 아무것도 강조되지 않는다 | 실제 열거일 때만 목록을 쓴다 |
| 모호한 동사 — 개선한다, 정리한다, 손본다, 보완한다(대상·기준 없이) | 무엇을 바꾸는지 알 수 없다 | 대상 파일·클래스·엔드포인트와 바뀌는 내용을 구체적으로 쓴다 |
| 판별 기준 없는 완료 조건 — 잘 동작하는지 확인한다, 문제없는지 검토한다 | 참/거짓을 가릴 수 없다 | 테스트명·명령·invariant ID로 검증 방법을 명시한다 |
| 같은 내용 반복 | 목적·범위·완료 조건에서 같은 문장을 되풀이한다 | 각 섹션은 서로 다른 정보만 담는다 |

## 3. 목적은 사실 중심으로, 3문장 이내로 스캔 가능하게

- 첫 문장: 현재 문제 또는 현재 상태.
- 둘째 문장: 왜 지금 다루는지(발견 경위, 트리거가 된 이슈·PR).
- 필요하면 셋째 문장: 이번 이슈가 다루는 경계(무엇까지 포함하고 무엇은
  아닌지 한 줄로).
- 관련 이슈가 여러 개면 배경을 풀어 쓰지 않고 이슈 번호만 인용한다
  (`#107이 남긴 자리`, `#153 위에 조립한다`처럼).

## 4. 범위는 실행 가능한 항목으로, 완료 조건은 검증 가능한 조건으로

- 범위의 각 항목은 대상(파일·클래스·함수·엔드포인트·테이블)을 명시한다.
  대상 없는 "관련 로직 개선" 같은 항목을 쓰지 않는다.
- 완료 조건은 참/거짓을 판별할 수 있는 문장으로 쓰고, 검증 방법(테스트명,
  검증 명령, invariant ID)을 함께 적는다.
- 아직 정해지지 않은 수치·정책은 확정된 것처럼 쓰지 않는다. `AGENTS.md`
  4.3절의 `CONFIRMED`/`ASSUMED`/`UNKNOWN`/`BLOCKED` 구분을 빌리거나
  "미결정"이라고 명시한다.

## 5. 사실과 추측을 구분한다

- 코드·로그·테스트 결과에서 확인한 사실과 아직 검증하지 않은 가정을
  구분해서 쓴다. "~일 것이다"로 뭉뚱그리지 않는다.
- 조사 중 발견한 기존 상태(예: 이미 존재하지만 아무도 호출하지 않는 함수)는
  근거(파일 경로, 이슈·PR 번호)와 함께 적는다.
- 이슈 작성자가 판단해야 할 미결정 사항, 제외 범위, 선행 관계를 빼지
  않는다.

## 6. 초안 제출 전 점검

- [ ] 이모지가 하나도 없는가
- [ ] 모든 서술이 `~한다`, `~했다`로 끝나는가(제목·완료 조건 예외 제외)
- [ ] 목적이 3문장 이내로 스캔 가능한가
- [ ] 범위의 각 항목에 구체적 대상이 있는가
- [ ] 완료 조건이 전부 참/거짓 판별 가능하고 검증 방법이 있는가
- [ ] 표의 금지 표현이 남아 있지 않은가
- [ ] 목적·범위·완료 조건이 같은 문장을 반복하지 않는가

하나라도 걸리면 고친 뒤에 사용자에게 초안을 보여준다.
