# ClickUp 작업과 GitHub 연결

기능명세서는 요구 동작을, ClickUp 스프린트 작업은 이번 주에 검증할 산출물을 관리한다.

## 입력 순서

1. 주간 계획에서 합의한 Backend Sprint 작업의 URL과 실제 task ID를 확인한다. 팀 스프린트 ID는 `QELLO-SYYYY-Www`로 별도 입력한다. 목록 ID를 작업 ID로 쓰지 않는다.
2. 백엔드 작업 Issue Form을 선택한다. 제목은 `[기능명세서 ID] 이번 주에 끝낼 산출물`로 쓰고, 명세가 없는 도구·기술부채 작업은 해당 없음과 사유를 기록한다.
3. 관찰 가능한 완료 조건 1~3개와 검증 방법을 적는다. 실행하지 않은 검증은 `미실행`으로 둔다.
4. 기존 하네스의 Issue 번호·브랜치·커밋·PR 연결 규칙에 따라 구현한다. GitHub의 canonical `type: *` 라벨과 ClickUp의 작업 종류 태그는 서로 다른 체계다.
5. PR에 ClickUp 작업 URL을 붙이고 ClickUp 작업 설명에 PR URL을 다시 붙인다. 리뷰어가 양쪽 링크와 검증 증빙을 확인한다.

## 작업 관리

- 담당자·기한·우선순위·상태는 ClickUp 기본 필드에서 합의해 관리한다.
- Android와 Backend는 별도 작업으로 만들고 같은 기능명세서 ID를 연결한다.
- 팀 전체 보드는 파트별 Sprint 목록을 조회한다. 같은 작업을 별도로 등록하지 않는다.
- ClickUp 태그는 `feature`, `bug`, `tech-debt`, `research`만 사용한다. 파트·상태·우선순위를 태그로 복제하지 않는다.
- 담당자 또는 완료 조건이 다른 독립 산출물만 서브태스크로 만든다. 구현·리뷰·테스트 단계는 체크리스트로 남긴다.
- 데일리에는 상태·막힘을 갱신하고, 주간 리뷰에서 완료 조건과 증빙을 확인한 뒤 완료로 바꾼다. PR 병합 자체를 작업 완료로 취급하지 않는다.
- 새 스프린트를 만들면 팀 보드의 Location/List 필터를 두 파트의 새 목록으로 바꾼다. 템플릿에는 특정 주차·목록 ID를 고정하지 않는다.

## 적용 범위와 제한

이번 변경은 백엔드 작업 폼과 기본 PR 템플릿의 연결을 다룬다. 기존 기능·버그·테스트·인프라 전용 폼과 전체 하네스 문서에는 GitHub Project 중심 안내가 남아 있으며, 이 변경에서 일괄 수정하지 않는다. 현재 팀의 일정·스프린트 운영은 사용자가 제공한 ClickUp 기준을 따른다.

Issue Form의 필수 입력은 빈 값 누락을 줄일 뿐 URL 형식·ID 일치·명세 존재를 자동 검증하지 않는다. PR 체크리스트도 서버에서 강제하는 검사가 아니므로 리뷰에서 확인한다. 템플릿은 기본 브랜치에 병합한 뒤 신규 Issue·PR에 적용되며 기존 본문을 자동 갱신하지 않는다.
