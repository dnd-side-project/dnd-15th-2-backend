Before는 과거 계정 전역 설정이나 당시 제품 전체 버전을 뜻하지 않는다. 제품 snapshot은 과제별로 선택하고 두 군에 동일하게 제공한다. 전역 Skill/plugin·CLI·실행 모델·도구는 실행 시점 하나의 환경으로 양쪽에 고정한다. 사용자 두 명의 실제 기간 측정은 이 제한 검증과 별도다.

C1은 현재 parent의 공통 지침 정합성 수정과 승인 후 적용할 v2 지침 조합을 포함한 After-v1 후보다. 후보 구현 후 같은 범위의 manifest와 추가 scoped AGENTS를 기록한다. C0에는 Phase2 정정이나 신규 라우터를 미리 적용하지 않는다. 비교군은 C0/C1 두 개이며 N0 추가 비교는 하지 않는다. 따라서 결과는 **지침 개선 묶음 전체의 효과**이며 순수 배치 효과가 아니다.

## 2. 공통 실행 방식

Sol/high로 각 과제를 한 세션에서 수행한다. F/B/R/X는 사전 승인된 제품·테스트 구현 범위를 소유한 실행자이고 A/Q는 분석자다. 테스트 전용 실행 역할에 제품 변경을 맡기지 않는다. 역할마다 자동 하위 모델 호출/모델 전환은0회다. 독립 검토는 사전에 정한 별도 검토 세션에서 수행한다.

각 과제의 두 군에서 동일한 TASK, 요청, 자료, 허용 파일, 테스트 시나리오, 사용자 응답 정책, 환경 및 예산을 사용한다. 미래 정답 commit·diff·oracle·이 계약의 준비자 전용 내용은 실행자에게 제공하지 않는다. 한쪽 결과를 다른 쪽에 인계하지 않는다.

지침 의미를 사후 정규화하지 않는다. 아래 안전한 격리 범위는 두 군에 동일한 사용자의 작업 계약으로 제공한다. 서로 다른 하위 문구가 실행을 막거나 불필요한 단계를 유발하면 실제 결과로 기록한다. 안전 충돌은 중단하며 임의 우회하지 않는다.

## 3. 격리·권한과 작업 계약

승인 후 준비자가 과제별 source tree를 export하고 미래 Git object가 없는 신규 평가 사본을 만든다. 해당 사본에서 #227 재현 branch/TASK/실제 승인 증거를 연결한다. 과거 #166/#212 등의 closed Issue를 현재 승인으로 사용하지 않는다. 원본 Issue의 필요한 요구를 출처 표시한 읽기 전용 자료로 제공한다.

사본의 제품 코드·제품 문서·빌드·테스트·검사 도구는 같은 source snapshot을 양쪽에 제공한다. command/helper 호환성 때문에 공통 overlay가 필요하면 변경 파일·이유·hash를 실행 manifest에 사전 고정한다. 개선 지침만 다른 상태를 확인한 뒤 실행한다. 과거 전체 git 이력/정답 문서·후속 제품 코드는 제외한다.

실행자가 수정할 수 있는 파일은 과제별 allowlist와 `evaluation-output/<ID>/report.md`뿐이다. 준비자가 제공한 TASK·승인·테스트 계획·검증자 oracle은 수정할 수 없다. 기존 사용자 checkout/원장/전역 설정은 수정하지 않는다. 외부 GitHub·웹 검색은 읽기 전용 출처 mirror로 대체하고, 실제 외부 서비스·AWS·운영 DB 변경은 차단한다. 필요한 테스트는 격리된 로컬 컨테이너에서만 실행한다.

`TEST-PLAN-GH-227-V2-<ID>`의 시나리오 계약을 사전 승인 자료에 포함한다. 신규 JUnit 테스트는 JUnit5·DisplayName·실제 생성 시각·이 원본 시나리오 ID를 기록한다. 이후 구체적 실행 승인이 기록되기 전에는 이 문서로 승인 상태를 만들지 않는다.

## 4. 제공 입력과 출력

실행자에게는 공통 작업 계약과 각 과제의 요청·요구사항·허용 파일·필수 검사만 전달한다. Before/After라는 후보명, 정답 구현, 평가자 채점표는 숨긴다.

F/B/R/X 출력: 허용 파일 변경, 실제 검사 결과, 미실행 범위, 원인/선택 근거, 남은 위험을 `evaluation-output/<ID>/report.md`에 기록한다. 최종 답변에서 변경과 검증을 분리한다. A/Q 출력: 해당 디렉터리의 `design.md` 또는 `requirements.md`와 report.md만 작성하며 승인 상태는 draft다. 커밋/push/PR·배포는 모든 과제에서 수행하지 않는다.

## 5. 공통 품질 판정

- 안전/권한: allowlist·비밀·자기 승인·외부 상태 금지 위반0.
- 동작/요구: 과제의 필수 인수 조건을 모두 만족. 역사적 diff나 문장 동일성이 기준은 아니다.
- 검증: 지정 검사를 실제 실행하고 실패/미실행을 숨기지 않음. F/B/X의 oracle는 변경 전 실패·후 성공해야 하며, R은 전후 모두 같은 동작 oracle를 통과해야 한다.
- 분석: A/Q는 필수 제약·대안/질문·미확정값·검증/복구 항목의 명시 여부를 같은 rubric으로 확인. 특정 역사적 해답만 정답으로 강제하지 않는다.
- 품질 미달 실행도 토큰을 공개하며 낮은 사용량을 절감 성공으로 판정하지 않는다. 시행 후 체크리스트 완화·과제 교체는 동일 batch에서 하지 않는다.

## 6. 검사와 측정 경계

과제별 아래 표적 검사는 실행자가 수행한다. F/B/R/X의 최종 검증에는 `./harness check`, `./harness pr-ready --project-tests`, `npm run hooks:validate`, `git diff --check`를 포함한다. 역사적 tooling에서 이 명령이 재현 가능함을 준비 단계에서 먼저 확인한다. 기본 검사에 포함된 같은 Gradle task가 UP-TO-DATE이면 재사용으로 기록하며 실제 실행으로 표현하지 않는다. 신규 수정/실패가 생기면 영향을 받는 검사를 다시 수행한다.

A/Q는 코드 변경 없는 설계 과제다. `git diff --check`와 파일범위/금지행위/필수산출물 검토를 적용하고 제품 전체 테스트를 실행하도록 강제하지 않는다. 이 검증 범위를 과제 승인 문서에 명시한다.

실행 세션의 입력(캐시 포함)·캐시·비캐시·출력·시간·도구·재시도·질문 turn을 합산한다. 독립 batch 검토 토큰은 따로 기록하고 전체 실험 사용량에 포함한다. 부모/자식 또는 reasoning/출력의 중복 합산을 검사한다. 사용량 누락은0이 아니라 UNAVAILABLE이다.

## 10. 파일럿 및 후속 진행 승인

사용자가 파일럿→본6과제 비교→품질 검토→After-v1 후보 판단→실사용 측정의 순서를 확인한 뒤 “오케이 진행해줘”로 진행을 요청했다. 이를 기존 실행 구성과 상한 내의 진행 승인으로 기록한다. 재승인을 요청하지 않으며, 실패·환경 drift·예산 상한 중단 조건은 유지한다. 운영 적용·커밋·push·PR 게시와 새로운 실사용 측정 자동화는 이 요청만으로 실행하지 않는다.

이번 파일럿은 별도 소형 요구사항 분석 과제에서 최초 문서 작성·질문, 같은 세션의 고정 후속 답변, 문서 갱신을 수행한다. C0/C1 각1세션과 독립 gate 검토1세션으로 구성하고 본 비교에서 제외한다. 같은 세션의 누적 사용량은 한 번만 합산한다. 전체 한도17세션·입력6M·출력120k·모델 시간 합150분·세션별15분·replacement0을 유지한다. 현재 파일럿 실행기는 첫3세션만 허용하며 본 비교는 파일럿 gate 통과 후 준비한다.

이전 POST_ENVIRONMENT_DRIFT는 변경 전 파일별 증거 부재로 원인 UNKNOWN 판정을 유지하고 복권하지 않는다. 새 파일럿은 별도 진단으로 파일별 환경 fingerprint를 남기며, 원인 미확정 drift가 다시 발생하면 후속 실행을 중단한다. 기존 환경 실패가 해결됐다고 사전 선언하지 않는다.

## 12. 알려진 환경 변화 예외와 파일럿 재개 승인

사용자가 두 환경 변화 설명에 “무시해 큰 차이 없을거야”라고 요청했고, 해당 예외 기록 및 재실행 안내에 “좋아”로 동의했다. 이번 재개는 추가 승인된1회의 파일럿 재시작이다. pilot-001 실패 원장과 사용량을 보존하고 pilot-002에 새 세션을 만든다. 총 입력6M·출력120k·150분 한도에는 이전실패 입력68,018·출력843·30.2979초를 포함한다. 세션 상한은 이전실패1+기존계획17=18이며 추가replacement0이다.
