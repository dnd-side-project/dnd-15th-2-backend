# Qello 인증 설계

> 작성일: 2026-08-06 (2026-08-07 갱신)
>
> 상태: 초안 (팀 검토 대기)
>
> 결정 근거: `docs/adr/0006-split-operator-and-device-authentication.md`

이 문서는 백오피스 운영자와 앱 사용자의 인증·세션 설계를 기술한다. 스키마,
API 계약, 패키지 구조, 미결 제품 결정을 포함한다.

## 1. 현재 상태

| 항목 | 현재 | 필요 |
| --- | --- | --- |
| `user_account` | `role`, `status`, 프로필 컬럼 | 변경 없음 |
| 운영자 비밀번호 | `V3`에서 `password_hash` 컬럼 추가 (main 병합 완료) | 로그인 식별자와 잠금 상태가 없어 로그인 불가. `V5`에서 `operator_credential`로 이동 |
| 비밀번호 해시 | `PasswordHasher` / `BCryptPasswordHasher` / `RawPassword` | 그대로 사용 |
| 기기 자격증명 | 없음 | 신규 |
| 세션·토큰 | 없음 | 신규 |
| Spring Security | `spring-security-crypto`만 의존 | starter 추가 필요 |
| 응답 본문 형식 | ADR-0005로 `ApiResponse` / `ApiErrorResponse` 고정 | 인증 엔드포인트도 이 계약을 따른다 |

`push_device` 테이블이 이미 있으나 이는 FCM/APNs 토큰 보관용이며 인증과 무관하다
(3.3 참고).

## 2. 두 인증 영역

| | 백오피스 (OPERATOR) | 앱 사용자 (USER) |
| --- | --- | --- |
| 주체 | 팀원 5명 내외, 고정 | 익명 대중, 무제한 |
| 클라이언트 | 브라우저 | iOS/Android 네이티브 |
| 인증 수단 | `login_id` + 비밀번호(bcrypt) | 서버 발급 `device_secret` |
| 자격증명 저장 위치 | 사람의 기억 / 비밀번호 관리자 | Keychain / Keystore |
| 세션 방식 | 서버 세션 + HttpOnly 쿠키 | 단기 access token (JWT) |
| 세션 수명 | idle 8h / absolute 12h | access 30분, 기기 자격증명 무기한 |
| 즉시 해지 | 세션 행 삭제로 즉시 | revoke 후 최대 30분 지연 |
| CSRF | 필요 | 불필요 (Bearer 헤더) |
| 계정 생성 | 자체 가입 없음 (시드/CLI) | 앱 최초 실행 시 자동 |

## 3. 스키마 설계

### 3.1 `operator_credential`

계정 생명주기(차단·삭제)와 자격증명 생명주기(비밀번호 교체·잠금)는 변경 주기가
다르므로 테이블을 분리한다. `user_account`에 인증 컬럼을 계속 추가하면 수백만
행의 일반 사용자가 운영자 5명 때문에 존재하는 NULL 컬럼을 들고 다니게 된다.

```sql
-- 복합 FK를 걸기 위한 준비
ALTER TABLE user_account
    ADD CONSTRAINT uq_user_account_id_role UNIQUE (id, role);

CREATE TABLE operator_credential (
    user_id                 BIGINT PRIMARY KEY,
    role                    VARCHAR(20) NOT NULL DEFAULT 'OPERATOR',
    login_id                VARCHAR(50) NOT NULL,
    password_hash           VARCHAR(255) NOT NULL,
    failed_attempt_count    SMALLINT NOT NULL DEFAULT 0,
    locked_until            TIMESTAMPTZ,
    password_updated_at     TIMESTAMPTZ NOT NULL DEFAULT clock_timestamp(),
    last_login_at           TIMESTAMPTZ,
    created_at              TIMESTAMPTZ NOT NULL DEFAULT clock_timestamp(),
    updated_at              TIMESTAMPTZ NOT NULL DEFAULT clock_timestamp(),

    CONSTRAINT fk_operator_credential_user
        FOREIGN KEY (user_id, role) REFERENCES user_account (id, role)
        ON DELETE CASCADE,
    CONSTRAINT ck_operator_credential_role
        CHECK (role = 'OPERATOR'),
    CONSTRAINT uq_operator_credential_login_id
        UNIQUE (login_id),
    CONSTRAINT ck_operator_credential_login_id
        CHECK (btrim(login_id) <> '' AND login_id = lower(login_id)),
    CONSTRAINT ck_operator_credential_failed_attempt
        CHECK (failed_attempt_count >= 0)
);

COMMENT ON TABLE operator_credential IS
    '백오피스 운영자 자격증명. 일반(USER) 계정은 행을 갖지 않는다. 평문 비밀번호는 저장하지 않는다.';
```

**복합 FK `(user_id, role)`** 가 이 설계의 핵심이다. PostgreSQL은 테이블 간 CHECK를
지원하지 않아 "USER 계정에 비밀번호가 붙는" 사고를 보통 애플리케이션 레벨로만
막는다. `(id, role)` 복합 FK를 쓰면 DB가 선언적으로 막고, `user_account.role`을
USER로 강등하는 순간 FK 위반으로 실패하므로 권한 강등 시 자격증명이 남는 사고도
차단된다. ADR-0002의 "DB constraint는 최종 무결성 경계" 원칙과 일치한다.

### 3.2 `device_credential`

```sql
CREATE TABLE device_credential (
    id                      BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    user_id                 BIGINT NOT NULL,
    installation_id         VARCHAR(64) NOT NULL,
    secret_hash             CHAR(64) NOT NULL,
    platform                VARCHAR(20) NOT NULL,
    credential_status       VARCHAR(20) NOT NULL DEFAULT 'ACTIVE',
    last_used_at            TIMESTAMPTZ NOT NULL DEFAULT clock_timestamp(),
    created_at              TIMESTAMPTZ NOT NULL DEFAULT clock_timestamp(),
    revoked_at              TIMESTAMPTZ,

    CONSTRAINT fk_device_credential_user
        FOREIGN KEY (user_id) REFERENCES user_account (id) ON DELETE CASCADE,
    CONSTRAINT ck_device_credential_platform
        CHECK (platform IN ('IOS', 'ANDROID')),
    CONSTRAINT ck_device_credential_status
        CHECK (credential_status IN ('ACTIVE', 'REVOKED')),
    CONSTRAINT ck_device_credential_revoked_at
        CHECK ((credential_status = 'REVOKED') = (revoked_at IS NOT NULL)),
    CONSTRAINT ck_device_credential_installation_id
        CHECK (btrim(installation_id) <> '')
);

CREATE UNIQUE INDEX uq_device_credential_secret
    ON device_credential (secret_hash);
CREATE UNIQUE INDEX uq_active_device_installation
    ON device_credential (installation_id) WHERE credential_status = 'ACTIVE';
CREATE INDEX device_credential_user_idx
    ON device_credential (user_id) WHERE credential_status = 'ACTIVE';
```

기존 `push_device`의 관례를 따랐다. `device_status` 대신 `credential_status`로
컬럼명을 한정하고, `(status = 'REVOKED') = (revoked_at IS NOT NULL)` 패턴과 ACTIVE
행 부분 unique index(`uq_active_push_token`과 동일한 방식)를 사용한다.

`user_id`에 1:N으로 설계해 두어 향후 다기기 지원 시 스키마 변경 없이 확장된다.

### 3.3 `push_device`와 분리하는 이유

같은 물리적 기기를 가리키지만 생명주기가 독립이다.

- 푸시 토큰은 FCM/APNs가 발급하고 수시로 갱신·무효화되는 **외부 소유** 값이다.
- 기기 자격증명은 우리가 발급하고 우리만 해지하는 **인증** 값이다.
- 푸시 토큰이 갱신됐다고 로그인이 풀리면 안 되고, 푸시 권한을 거부한 사용자도
  로그인은 되어야 한다.

## 4. 앱 사용자 인증

### 4.1 절대 규칙: 클라이언트가 만든 ID는 인증 수단이 아니다

```text
[금지] 앱이 UUID 생성 → 서버에 전송 → 서버가 그 UUID로 계정 식별하고 토큰 발급
```

이 구조에서는 UUID를 아는 사람이 곧 계정 주인이 된다. 로그에 한 번 남거나 프록시
구간에서 새면 그대로 계정 탈취다. 비밀번호를 클라이언트가 정해 평문으로 보내는
것과 같다.

```text
[채택] 앱이 installation_id 생성(단순 식별자)
     → 서버가 계정 생성 + SecureRandom 32바이트 device_secret 발급
     → 발급 응답에서 단 한 번만 평문 노출
     → 앱이 Keychain/Keystore에 저장
     → 이후 인증은 device_secret으로만 수행
```

### 4.2 해시 알고리즘: `device_secret`에 bcrypt를 쓰지 않는다

| 대상 | 엔트로피 | 알고리즘 | 이유 |
| --- | --- | --- | --- |
| 운영자 비밀번호 | 낮음 (사람이 정함) | bcrypt | 무차별 대입을 느리게 만들어야 함 |
| `device_secret` | 256bit 랜덤 | SHA-256 | 대입 불가. 인덱스 조회가 필요 |

bcrypt는 salt가 매번 달라 `WHERE hash = ?` 조회가 불가능하고, 요청마다 수십~수백
ms의 CPU를 소모한다. 고엔트로피 랜덤 시크릿에는 고정 해시가 맞다.

### 4.3 최초 등록

```http
POST /api/v1/auth/devices
Content-Type: application/json

{
  "installationId": "a3f1...",
  "platform": "IOS",
  "coarseRegionCode": "KR-11",
  "locale": "ko-KR",
  "timezone": "Asia/Seoul",
  "nickname": "바람"
}
```

```http
201 Created

{
  "userId": 1024,
  "deviceSecret": "<base64url 32 bytes>",
  "accessToken": "eyJ...",
  "expiresIn": 1800
}
```

서버 처리 (단일 트랜잭션):

1. `installation_id`로 ACTIVE 자격증명 조회. 존재하면 409 Conflict.
2. `Account.createUser(coarseRegionCode, locale, timezone, nickname)` 호출.
3. `AccountRepository.save()`.
4. `SecureRandom` 32바이트 생성 → SHA-256 → `device_credential` insert.
5. Access token 발급.

`coarseRegionCode`, `locale`, `timezone`은 `user_account`에서 NOT NULL이고
`Account` 도메인 생성자가 요구하므로 등록 요청에 포함해야 한다. 앱이 최초 실행
시 이 값을 확보한 뒤 등록을 호출하는 순서가 되어야 하며, 클라이언트 팀과 합의가
필요한 지점이다.

`deviceSecret`은 이 응답에서만 평문으로 존재한다. 로그, APM, 에러 응답에 절대
포함하지 않는다. 기존 `RawPassword`/`PasswordHash`와 동일하게 `toString()`을
`REDACTED`로 재정의한 `DeviceSecret` record를 사용한다.

### 4.4 토큰 재발급

```http
POST /api/v1/auth/token

{ "installationId": "a3f1...", "deviceSecret": "..." }
```

```http
200 OK

{ "accessToken": "eyJ...", "expiresIn": 1800 }
```

서버 처리:

1. `secret_hash = sha256(deviceSecret)`로 조회. `installationId`는 교차 검증용.
2. `credential_status = 'ACTIVE'` 확인.
3. **`user_account.status` 확인.** BLOCKED/DELETED면 403. 차단이 반영되는 지점이다.
4. `last_used_at` 갱신.
5. Access token 발급.

클라이언트는 401 응답 시 재발급을 시도하고, 재발급도 401/403이면 로그아웃 상태로
전환한다. **동시에 발생한 여러 401이 재발급을 중복 호출하지 않도록 앱 인터셉터에서
단일화**해야 한다. 클라이언트 요구사항으로 전달한다.

### 4.5 Access token

```json
{
  "iss": "qello",
  "sub": "1024",
  "aud": "qello-app",
  "role": "USER",
  "did": 5521,
  "jti": "...",
  "iat": 1754400000,
  "exp": 1754401800
}
```

`spring-boot-starter-oauth2-resource-server`의 Nimbus 구현
(`NimbusJwtEncoder` / `NimbusJwtDecoder`)으로 발급·검증한다. JWT 필터를 직접
작성하지 않아 서명·클레임 검증을 검증된 구현에 위임할 수 있다. 단일 서비스이므로
HS256으로 충분하며, 서명 키는 환경변수로만 주입한다(저장소·로그 기록 금지).

### 4.6 즉시 차단

JWT는 stateless라 차단 반영이 최대 TTL만큼 지연된다. 단계적으로 대응한다.

1. **기본**: access token TTL을 15~30분으로 유지하고, 재발급 시 계정 상태를
   확인한다.
2. **필요 시**: 차단 사용자 ID 캐시(Caffeine, TTL 30초)를 필터에서 조회한다.
   정상 사용자는 캐시 히트로 DB 부하가 거의 없고 차단은 30초 내 반영된다.

2단계는 스키마 변경 없이 추가할 수 있으므로 F08(신고·차단) 정책 확정 후 도입해도
된다.

## 5. 백오피스 인증

### 5.1 로그인

로그인 POST에도 CSRF를 적용하므로(login CSRF 방어) 클라이언트는 먼저 토큰을 받아야 한다.
`/admin/**`은 이 GET 하나와 로그인 POST를 빼면 전부 인증이 필요하다. 이 경로가 없으면
토큰을 얻을 방법이 없어 로그인 자체가 불가능하다.

```http
GET /admin/csrf
```

```http
200 OK
Set-Cookie: XSRF-TOKEN=...; Path=/

{ "status": "success", "data": { "headerName": "X-XSRF-TOKEN", "token": "..." },
  "timestamp": "2026-08-07T09:00:00Z" }
```

토큰은 인증 상태와 무관한 값이라 노출해도 안전하다. 방어의 근거는 공격자가 피해자의
브라우저에서 이 응답을 읽을 수 없다는 same-origin 정책이다.

```http
POST /admin/login
X-XSRF-TOKEN: ...

{ "loginId": "...", "password": "..." }
```

```http
200 OK
Set-Cookie: SESSION=...; HttpOnly; Secure; SameSite=Lax; Path=/
Content-Type: application/json

{ "status": "success", "data": { "userId": 1024 }, "timestamp": "2026-08-07T09:00:00Z" }
```

ADR-0005가 204 No Content를 쓰지 않기로 했으므로 성공 응답도 200과 `ApiResponse` 형식으로
나간다. 세션 자체는 본문이 아니라 `Set-Cookie` 헤더로 전달하고, 본문에는 화면 구성에 필요한
식별자만 담는다. 이 문서 초안은 204를 썼으나 응답 계약에 맞춰 고쳤다.

서버 처리:

1. `locked_until > now()` → 423 Locked.
2. `passwordHasher.matches(rawPassword, passwordHash)` (기존 `BCryptPasswordHasher`).
3. 실패 시 `failed_attempt_count + 1`. 5회 도달 시 `locked_until = now() + 15분`.
4. 계정 상태가 `ACTIVE`가 아니면 403(`AUT-APP-003`). 차단이 세션에 반영되는 지점이다.
5. 성공 시 카운터 0, `last_login_at` 갱신, **세션 ID 재발급**(session fixation 방어).

실패 판정은 트랜잭션을 rollback시키지 않는다. `AuthException`으로 rollback되면 실패 카운터
증가가 함께 사라져 잠금이 영원히 걸리지 않는다. 로그인 실패는 "실패를 기록하고 거절한다"는
하나의 성공한 처리다.

### 5.2 부수 요구사항

- **계정 열거 방지**: 실패 응답을 `AUT-APP-001` 하나로 통일하고, 계정이 없을 때도 더미
  bcrypt 검증을 수행해 응답 시간 차이를 없앤다. 더미 해시는 상수로 두지 않고 기동 시
  실제 hasher로 만든다. 형식이 어긋나면 `BCryptPasswordEncoder`가 비교를 건너뛰어
  방어가 조용히 사라지고, cost factor가 바뀌면 비용도 달라진다.
- **세션 저장소**: Spring Session JDBC를 사용해 기존 PostgreSQL만으로 처리한다.
  팀 5명 규모에 Redis를 별도로 도입하지 않는다.
- **CSRF**: 쿠키 기반이므로 상태 변경 요청에 CSRF 토큰을 요구한다.
- **도메인 배치**: 백오피스를 `admin.qello.app`, API를 `api.qello.app`처럼 같은
  등록 도메인 하위에 두면 `SameSite=Lax`로 XHR이 동작한다. 다른 등록 도메인에
  두면 `SameSite=None` + CORS credential 구성이 필요해 복잡도가 크게 는다.
  **서브도메인 배치를 전제로 설계한다.**
- **운영자 계정 생성 API를 만들지 않는다.** 자체 가입 엔드포인트는 그 자체가 공격면이다.
  대신 `qello.auth.operator-seed.enabled=true`일 때만 동작하는 기동 시 시더로 만들고,
  `login-id`와 `password`는 환경변수로만 주입한다. Flyway 시드 migration을 쓰지 않는
  이유는 해시가 저장소에 남아 모든 환경이 같은 비밀번호를 갖게 되고, 바꾸려면 이미
  적용된 migration을 고쳐야 하기 때문이다.
- **초기 비밀번호 강제 변경은 아직 구현하지 않았다.** `password_updated_at`으로 판단할
  준비만 돼 있다.

## 6. Spring Security 구성

추가 의존성:

```gradle
implementation 'org.springframework.boot:spring-boot-starter-security'
implementation 'org.springframework.boot:spring-boot-starter-oauth2-resource-server'
implementation 'org.springframework.session:spring-session-jdbc'
```

경로 기준으로 `SecurityFilterChain`을 분리한다.

```java
@Bean
@Order(1)
SecurityFilterChain backofficeChain(HttpSecurity http) throws Exception {
    return http
        .securityMatcher("/admin/**")
        .sessionManagement(s -> s
            .sessionCreationPolicy(SessionCreationPolicy.IF_REQUIRED)
            .sessionFixation().newSession())
        .csrf(c -> c.csrfTokenRepository(CookieCsrfTokenRepository.withHttpOnlyFalse()))
        .authorizeHttpRequests(a -> a
            .requestMatchers(HttpMethod.GET, "/admin/csrf").permitAll()
            .requestMatchers(HttpMethod.POST, "/admin/login").permitAll()
            .anyRequest().hasRole("OPERATOR"))
        .exceptionHandling(h -> h
            .authenticationEntryPoint(authEntryPoints.unauthorized())
            .accessDeniedHandler(authEntryPoints.forbidden()))
        .build();
}

@Bean
@Order(2)
SecurityFilterChain appApiChain(HttpSecurity http) throws Exception {
    return http
        .securityMatcher("/api/**")
        .sessionManagement(s -> s
            .sessionCreationPolicy(SessionCreationPolicy.STATELESS))
        .csrf(CsrfConfigurer::disable)
        .oauth2ResourceServer(o -> o.jwt(Customizer.withDefaults()))
        .authorizeHttpRequests(a -> a
            .requestMatchers("/api/v1/auth/devices", "/api/v1/auth/token").permitAll()
            .anyRequest().hasRole("USER"))
        .build();
}

// 두 체인 어디에도 매칭되지 않는 경로를 막는다.
@Bean
@Order(Ordered.LOWEST_PRECEDENCE)
SecurityFilterChain fallbackChain(HttpSecurity http) throws Exception {
    return http
        .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
        .csrf(CsrfConfigurer::disable)
        .authorizeHttpRequests(a -> a.anyRequest().denyAll())
        .build();
}
```

두 체인이 서로의 설정을 오염시키지 않는 것이 이 구조의 핵심 이득이다. 백오피스에서
CSRF가 꺼지거나 앱 API에 세션이 생기는 사고가 구조적으로 차단된다.

**fallback 체인이 필요한 이유**는 매칭되는 체인이 없는 요청을 Spring Security가 그대로
통과시키기 때문이다. `/admin`과 `/api` 밖의 경로가 인증 없이 열리는 것을 막는다.

**필터 단계에서 끝나는 401·403은 `GlobalExceptionHandler`를 거치지 않는다.** 그대로 두면
그 두 상태만 응답 계약을 벗어나므로, `AuthEntryPoints`가 같은 `ApiErrorResponse` 형식으로
직접 써 준다.

`spring-security-test`의 `csrf()` request post-processor는 `TestCsrfTokenRepository`를
설치해 설정된 `CookieCsrfTokenRepository`를 덮어쓴다. 그 효과가 같은 테스트 클래스의 뒤
요청까지 새므로, 통합 테스트는 `GET /admin/csrf`로 받은 실제 토큰을 쓴다.

## 7. 패키지 구조

기존 feature-first 레이아웃을 따라 `auth`를 최상위 feature로 둔다. 운영자와 앱

## 8. 미결 제품 결정

설계보다 이쪽이 선행 과제다. 코드로 해결할 수 없고 팀이 정해야 한다.

### 8.1 기기를 잃으면 계정도 잃는다

익명 + 기기 바인딩의 필연적 귀결이다. 기기 교체나 앱 삭제 시 그동안의 글·답변·
닉네임이 모두 사라진다. Android는 앱 삭제 시 Keystore 항목이 제거되고 iOS
Keychain도 보존을 보장할 수 없다.

| 선택지 | 구현 비용 | 비고 |
| --- | --- | --- |
| (a) 수용하고 제품에 안내 | 없음 | 8주 프로젝트에서 현실적 |
| (b) 복구 코드 1회 발급 | 작음 (테이블 1개) | 다기기 지원까지 함께 해결 |
| (c) 소셜 계정 연동 | 큼 | 익명성 컨셉과 충돌 |

**(b) 권장.** `device_credential` 스키마를 그대로 두고 `account_recovery_code`
테이블만 추가하면 되며, 8.3의 다기기 문제도 같은 메커니즘으로 풀린다.

### 8.2 계정 무한 생성(sybil) 방어가 없다

등록 엔드포인트가 인증 없이 열려 있어 스크립트로 계정을 무제한 생성할 수 있다.
익명 서비스이므로 F08 차단이 무력화되고(차단당하면 새 계정 생성) F10 안전 필터도
우회된다.

- **1차 (필수)**: IP 단위 등록 rate limit.
- **2차**: Play Integrity API / App Attest 기기 무결성 검증. 스키마 변경 없이
  추가 가능.

### 8.3 다기기 사용은 현재 설계로 불가능하다

새 기기는 자신이 기존 사용자임을 증명할 수단이 없어 새 계정이 된다.
`device_credential`을 1:N으로 설계해 두었으므로 8.1의 (b)를 채택하면 자연히
열린다. 현 스프린트에서 지원할지 여부만 결정하면 된다.

### `password_hash` 이전 경로

이 문서 초안은 `V3__add_user_account_password_hash.sql`이 main에 없다는 전제로
"지금 조정하면 마이그레이션 1개로 끝난다"고 적었다. #48이 병합되어 main에 `V3`와
`V4`가 적용됐으므로 그 선택지는 닫혔다.

적용된 마이그레이션은 수정하지 않는다(`AGENTS.md`, ADR-0001). #72에서 `V5`를 새로
추가해 다음을 한 번에 처리한다.

- `operator_credential` 테이블 생성
- `user_account (id, role)` 복합 unique 추가
- `user_account.password_hash` 컬럼과 `ck_user_account_password_hash` 제거

현재 운영자 계정이 없어 백필할 데이터가 없으므로 컬럼 제거를 같은 버전에서 함께
수행할 수 있다. 운영 데이터가 생긴 뒤라면 "추가 → 백필 → 제거"를 별도 버전으로
나눠야 한다.
