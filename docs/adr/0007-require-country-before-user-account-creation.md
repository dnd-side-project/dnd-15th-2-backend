# ADR-0007. 일반 사용자 계정 생성 전에 국가를 검증한다

## 배경

앱 사용자는 별도 회원가입 없이 `POST /api/v1/auth/devices`에서 일반 계정, 기기
자격증명과 첫 access token을 한 번에 발급받는다. 온보딩에서 국가를 필수로
선택해야 하며, 국가가 없거나 유효하지 않으면 서비스를 사용할 수 없어야 한다.

국가를 입력하지 않은 일반 계정을 먼저 만들면 기기 자격증명이 없는 고아 계정이
남고, 이를 다시 식별하고 복구하기 위한 비인증 온보딩 세션이 추가로 필요하다.
운영자 계정은 별도 시드 경로에서 생성되므로 국가 필수 조건을 적용하지 않는다.

## 고려한 선택지

1. 국가 없이 일반 계정을 먼저 만들고 `INACTIVE` 상태로 저장한다.
2. 별도 온보딩 세션을 만든 뒤 국가 입력이 완료되면 계정으로 전환한다.
3. 기존 기기 등록 요청에서 국가를 검증하고 성공한 경우에만 계정과 자격증명을
   원자적으로 생성한다.

## 결정

선택지 3을 채택한다.

앱은 화면에 현지화된 국가명을 표시하지만 API에는 자유 입력 국가명이 아니라
ISO 3166-1 alpha-2 `countryCode`를 보낸다. 서버는 앞뒤 공백 제거와 대문자 변환 후
다음 조건을 모두 확인한다.

1. 값이 누락되거나 공백이 아니고 국가 코드 형식에 맞는다.
2. `region_code` 마스터에 같은 코드가 존재하고 `level = 'COUNTRY'`다.
3. 함께 전달된 `coarseRegionCode`가 같은 국가를 최상위 조상으로 가진다.

검증은 계정 저장보다 먼저 수행한다. 하나라도 실패하면 HTTP 400을 반환하고
`user_account`, `device_credential`과 access token을 생성하지 않는다. 검증에
성공하면 기존처럼 계정 생성, 기기 자격증명 저장과 첫 토큰 발급을 단일 트랜잭션으로
처리한다.

누락·공백은 공통 필수값 오류로 처리하고, 형식 오류·미지원 코드·COUNTRY가 아닌
코드·지역 계층 불일치는 신규 `AUT-VAL-004 INVALID_COUNTRY_CODE`로 통일한다. 오류
응답과 로그에는 사용자가 제출한 원문을 포함하지 않는다.

`user_account`에는 화면 표시 이름을 복사하지 않고 정규화된 `country_code`를
저장한다. 표시 이름은 `region_code.display_name`에서 조회한다. 국가명 변경이나
현지화 때문에 계정 데이터가 달라지는 일을 막기 위한 결정이다.

DB는 다음 불변식을 강제한다.

- `role = 'USER'`이면 `country_code`는 반드시 존재한다.
- `role = 'OPERATOR'`이면 `country_code`는 `NULL`일 수 있다.
- 값이 존재하는 `country_code`는 `region_code`의 `COUNTRY` 행만 참조한다.

마지막 조건은 `(code, level)` 복합 참조로 강제한다. `region_code`에 `(code, level)`
UNIQUE를 추가하고, `user_account`에는 `country_code`와 항상 `COUNTRY`를 나타내는
생성 컬럼을 둔 뒤 복합 FK로 연결한다. 애플리케이션 검증과 별개로 직접 SQL이나
경합에서도 하위 지역 코드가 국가로 저장되지 않게 한다.

기존 일반 사용자는 저장된 `coarse_region_code`의 지역 계층을 따라 최상위
`COUNTRY`를 찾아 `country_code`를 이관한다. 이는 저장소 내부의 기존 관계를
사용하는 결정적 변환이며 외부 데이터 추정이 아니다. 최상위 국가를 정확히 하나로
확정할 수 없는 일반 사용자 행이 있으면 migration을 중단한다. 운영자는 국가를
채우지 않는다.

국가는 이번 범위에서 계정 생성 시 한 번 정해지며 변경 API는 추가하지 않는다.

## 선택 이유

- 국가가 없는 일반 계정과 자격증명이 없는 고아 계정이 생기지 않는다.
- 기존 기기 등록의 원자성과 복구 규칙을 유지한다.
- 비인증 온보딩 토큰, 만료와 정리 작업을 새로 도입하지 않는다.
- 국가 표시 문자열 대신 안정적인 코드로 참조 무결성과 현지화를 분리한다.
- 운영자 인증 경로에 앱 온보딩 정책을 전파하지 않는다.

## 결과

### 장점

- 국가 검증 실패의 저장 결과가 항상 0건이라 재시도가 단순하다.
- `USER`와 국가의 관계를 애플리케이션과 DB에서 함께 보장한다.
- 현재 `ACTIVE`, `BLOCKED`, `DELETED` 상태 모델을 변경하지 않는다.

### 단점

- 기기 등록 요청과 계정 영속 모델에 `countryCode`가 추가된다.
- 국가 코드와 `coarseRegionCode`의 계층 일치 검증이 필요하다.
- 기존 사용자 이관 전에 지역 계층 데이터의 완전성을 확인해야 한다.
- 이전 앱 버전은 필수 필드를 보내지 않아 신규 기기 등록이 실패한다.

## 배포와 복구

1. `region_code`의 COUNTRY 코드가 ISO 3166-1 alpha-2 형식인지, 모든 기존 USER의
   `coarse_region_code`가 최상위 COUNTRY 하나로 연결되는지 읽기 전용으로 확인한다.
2. `countryCode`를 보내는 앱 버전을 먼저 배포한다. 기존 백엔드는 추가 필드를
   무시하므로 이 단계에서는 기존 등록 계약이 유지된다.
3. 새 Flyway migration과 국가 필수 검증 백엔드를 함께 배포한다. migration은 컬럼
   추가, 기존 USER 이관, FK·CHECK 활성화를 한 트랜잭션에서 수행한다.
4. 이전 앱 버전의 신규 등록은 400으로 거절되므로 최소 지원 버전 안내와 업데이트
   경로를 제공한다. 기존 자격증명의 토큰 재발급에는 `countryCode`를 다시 요구하지 않는다.

새 제약이 적용된 상태에서 국가 필드를 모르는 이전 백엔드로 단독 롤백하면 신규 USER
insert가 실패한다. 적용된 migration을 수정하거나 삭제하지 않고 roll-forward를
우선한다. 호환성 복구가 필요하면 국가 데이터는 보존한 채 제약 적용 순서만 조정하는
새 migration과 별도 사람 승인을 사용한다.

기존 USER 백필과 제약 검증은 테이블과 인덱스에 부하를 줄 수 있다. 구현 전 실제 행
수와 잠금 영향을 확인하고, 허용 가능한 배포 시간 안에 끝나지 않으면 column 추가,
백필, 제약 검증을 별도 migration으로 나누는 계획을 다시 승인받는다.

이 ADR은 사용자 지시에 따라 구현 대상으로 승인되었다. 구현 후 테스트 결과와
PM/리뷰어 검토를 별도로 기록한다.
