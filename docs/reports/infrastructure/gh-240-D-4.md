## 1. Context and constraints

- Product stage: D-3(#229/#233/#237)로 EC2 테스트 서버·ECR 리포지토리가
  이미 설계·구현되었다(Terraform 코드는 존재하나 `terraform apply`는 아직
  실행되지 않았다 — 실제 리소스는 없다). 이번 설계는 그 위에 GitHub
  Actions가 이미지를 push하고 배포 명령을 보낼 IAM Role 하나만 추가한다.
- Expected workload: #231 workflow의 실행 빈도만큼(`main` push + 수동
  `workflow_dispatch`). 새로운 컴퓨팅·데이터베이스·트래픽을 만들지 않는다.
- Availability target: 해당 없음(IAM Role은 가용성 목표 대상이 아니다).
- Recovery target: 해당 없음. Role 삭제·재생성에 데이터 손실이 없다.
- Cost ceiling: **CONFIRMED — 추가 비용 없음.** IAM Role·Policy 자체는
  AWS가 과금하지 않는다(공식 문서: IAM은 무료). ECR push·SSM SendCommand
  호출 비용은 이미 D-3 설계·#231 이슈 범위의 워크로드에 포함되어 있고, 이
  Role은 기존 리소스에 대한 권한만 추가한다.
- Region assumption: **CONFIRMED — `ap-northeast-2`**(D-1/D-3에서 이미
  확정, `infra/bootstrap`과 동일 계정·리전).

실제 서버 주소, 계정 ID, IAM ID, 토큰, `.env` 값은 기록하지 않는다.

## 2. Proposed baseline

- Network: 변경 없음.
- Application workload: 변경 없음. 컨테이너 이미지 자체(Dockerfile)도
  변경하지 않는다.
- Database: 해당 없음.
- Storage: 해당 없음(ECR 리포지토리는 #229/#233에서 이미 설계·구현됨).
- Observability: GitHub Actions 실행 로그가 배포 이력을 대체한다. 별도
  CloudTrail 변경은 이번 범위에서 다루지 않는다(계정에 기존 Trail
  없음 — D-1 §1 참고, 이 상태는 여전히 유효하다).
- Backup: 해당 없음(IAM 리소스, 상태 없음).
- Deployment: `terraform plan`은 PR 정적 검사로 실행한다. `apply`는
  보호된 `infrastructure-apply` GitHub Environment workflow에서만
  실행하며 이 세션에서는 실행하지 않는다. 신설 Role 자체가 새 배포
  파이프라인의 신뢰 경계이므로 §5에서 상세히 다룬다.

## 5. Security and IAM

- GitHub OIDC trust boundary: 기존 `aws_iam_openid_connect_provider.github`
  (D-1에서 생성)를 재사용한다. 새 Role의 신뢰 정책은 `aud =
  sts.amazonaws.com`과 `sub LIKE repo:<org>/<repo>:ref:refs/heads/main`
  조건을 모두 요구한다. `infra_apply_trust`(환경 이름 조건)와 달리 이 Role은
  GitHub Environment를 조건으로 쓰지 않는다 — Environment 게이트 도입
  여부는 §15의 사람 결정 사항이다.
- Runtime role: 해당 없음(이 Role은 EC2에서 실행되지 않고 GitHub Actions
  워크플로가 직접 assume한다).
- Deployment role(신규, 가칭 `${project_prefix}-test-server-deploy`):
  - ECR: `ecr:GetAuthorizationToken`(AWS 제약상 리소스 수준 불가, `"*"` —
    D-3의 EC2 인스턴스 Role과 동일 근거), `ecr:BatchCheckLayerAvailability`,
    `ecr:InitiateLayerUpload`, `ecr:UploadLayerPart`,
    `ecr:CompleteLayerUpload`, `ecr:PutImage`, `ecr:BatchGetImage`,
    `ecr:DescribeRepositories`를 `arn:aws:ecr:*:*:repository/${project_prefix}-*`로
    한정한다(D-3 `ManageTestServerEcr` statement와 동일 패턴).
  - SSM: `ssm:SendCommand`를 EC2 인스턴스(`aws:ResourceTag/Project = qello`
    조건으로 한정, D-3의 `test_server_shared_permissions`와 동일 태그
    조건 재사용)와 `arn:aws:ssm:ap-northeast-2::document/AWS-RunShellScript`
    양쪽에 허용한다(SendCommand는 대상 인스턴스와 문서 양쪽에 대한 권한이
    모두 필요 — AWS 문서: SSM 리소스 수준 권한). `ssm:GetCommandInvocation`,
    `ssm:ListCommandInvocations`로 실행 결과를 조회한다.
  - **확인 필요(빌드 단계)**: SSM 관련 action 중 일부(`GetCommandInvocation`
    등)는 리소스 수준 권한을 지원하지 않을 수 있다(AWS 문서 확인 필요).
    D-3 빌드에서 `policy_sentry`로 EC2 action의 리소스 수준 지원 여부를
    검증했던 것과 같은 절차를 SSM action에도 적용한다. `Resource = "*"`가
    불가피한 action이 있다면 그 사실과 근거를 PR에 기록한다.
  - `iam:PassRole`은 필요 없다(인스턴스를 새로 만들지 않는다).
- Least-privilege actions: 위 목록 외 action을 추가하지 않는다.
  `arn:aws:iam::*:role/${project_prefix}-*` 같은 IAM 관리 권한, Terraform
  State 접근 권한(`infra-apply`가 갖는 `s3:*`/`kms:*`)은 이 Role에 부여하지
  않는다.
- Encryption: 해당 없음(이 Role 자체는 데이터를 암호화하지 않는다. ECR는
  기본 암호화가 이미 D-3 범위).
- Network restrictions: 해당 없음(IAM 리소스, 네트워크 경계 없음).
- Audit logging: CloudTrail 관리 이벤트(기본 활성화, 90일 조회 가능)로
  `AssumeRoleWithWebIdentity`와 `SendCommand` 호출이 기록된다. 전용 Trail
  신설은 D-1에서 이미 범위 밖으로 결정했고 이번 설계도 그 결정을 따른다.

## 9. IaC plan

- IaC choice: `Terraform`(ADR-0004, AGENTS.md 4.1)
- Module/stack boundaries: `infra/bootstrap/oidc.tf`에 기존 `infra_plan_trust`/
  `infra_apply_trust`와 같은 위치·패턴으로 `test_server_deploy_trust`,
  `aws_iam_role.test_server_deploy`, `test_server_deploy_permissions`를
  추가한다. 새 모듈이나 새 environment 디렉터리는 만들지 않는다.
- State storage: `infra/bootstrap`의 기존 S3 Backend를 그대로 사용한다
  (D-1에서 이미 구성).
- Locking: 기존 `use_lockfile` 설정을 그대로 사용한다(변경 없음).
- Plan command: `terraform -chdir=infra/bootstrap init -backend=false` +
  `validate`(이번 세션). 실제 `plan`은 빌드 단계에서 승인된 환경이 준비된
  경우에만 실행한다.
- Drift detection: 별도 스케줄 없음(D-1/D-3와 동일 결정 유지).

## 11. Decision

- Recommendation: `infra/bootstrap/oidc.tf`에 GitHub Actions 전용 배포
  Role을 신설한다. 신뢰 정책은 `sub`를 `repo:<org>/<repo>:ref:refs/heads/main`
  으로 한정하고, 권한은 ECR push(리포지토리 ARN 한정)와 SSM
  SendCommand(태그+문서 ARN 한정)로만 좁힌다. `infra-deployer`·`infra-apply`
  재사용은 신뢰 정책·권한 범위가 맞지 않아 제외한다(§4).
- Deferred alternatives: GitHub Environment 게이트 도입(요구하지 않기로
  결정, 2026-09-17 — Issue #231의 자동 배포 의도를 유지), SSM 대신 SSH
  기반 배포(Issue #231이 이미 "SSH 접속 경로를 만들지 않는다"고 제외함).
- Reviewer comments: tkv00 — "APPROVED_FOR_BUILD로 승인, sub claim은
  ref:refs/heads/main만 허용, Environment 게이트 요구하지 않음, Role
  이름 확정"(2026-09-17). 설계 단계 승인이며, PR 코드 승인·Environment
  승인은 `/harness-infra-build` 산출물에 대해 별도로 받는다.

## 12. Failure modes

- 신뢰 정책 오설정으로 `sts:AssumeRoleWithWebIdentity`가 실패 → workflow가
  자격 증명 단계에서 명시적으로 실패한다(조용히 넘어가지 않는 안전한 실패).
- SSM `SendCommand` 대상 조건 오설정으로 명령이 전송되지 않음 → workflow가
  SendCommand 응답에서 실패를 감지해야 한다(#231 구현 시 확인 필요, 이번
  설계 범위 밖).
- ECR 권한 누락으로 push 실패 → workflow가 `docker push` 오류로 명확히
  실패한다.
