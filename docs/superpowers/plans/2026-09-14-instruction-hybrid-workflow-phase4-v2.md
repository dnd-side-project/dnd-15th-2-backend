## 1. 목적과 기존 결과의 취급

사용자의 목적은 일반 기능 구현, 버그 수정, 리팩터링, 아키텍처 설계, 요구사항 분석과 복합 요청의 세션 비용 최적화다. 테스트/인프라 지침 읽기만으로 대표하지 않는다.
B2/B3는 선택적으로 조합할 배치 방식이다. 전체 우승 구조나 모델을 선정하는 실험으로 고정하지 않는다. 조합하면 반드시 유리하다는 결론도 미리 두지 않는다.

Phase1~3의 원장·보고서는 그대로 보존한다. Phase4 기존7파일의 TEST_SCOPED 변경도 자동 폐기하거나 최종 채택하지 않는다. 새 후보를 만들기 전에 해당 미커밋 diff와 새 파일을 비공개 snapshot/hash로 보존하고, 후보 사본에서만 새 구성을 만든다.
기존 회귀1회는 POST_ENVIRONMENT_DRIFT,입력421601·출력8214·185.64초로 보존한다. 과거 나머지3회 및 실패1+신규4회 재개 제안은 이번 재설계로 보류되며 자동 실행하지 않는다. 새 예산은 과거 예산 잔액을 승계한 승인이 아니다.

## 2. 공식 근거와 적용 해석

OpenAI 공식 글: https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra
확인일:2026-09-14. 짧고 정확한 Skill 호출 조건, 필요한 상세 내용의 점진적 로딩, 과도한 절차/전역 필수 읽기 재검토, 여러 모델 사용자 고려를 설계 원칙으로 사용한다.

공식 지침을 이유로 저장소의 안전·승인·권한 규칙을 삭제하지 않는다. 명시적 필수 검사는 유지하고 검증 단계 사이의 불필요한 재실행을 구분한다. 정책 의미 변경이 필요한 제안은 위치 이동과 분리해 사람 판단 항목으로 제시한다.
제한 검증의 모델/effort는 기존 실험과 연결 가능한 Sol/high 하나로 고정하는 안이다. 이는 측정 조건이며 실제 사용자의 모델 선택이나 역할 배분을 규정하지 않는다. Astra를 포함한 여러 모델에서 사용할 공통 지침으로 설계하되, 이번 결과를 다른 모델의 절감률로 일반화하지 않는다.

## 3. 지침 배치 원칙

| 분류 | 소유 위치 | 배치 기준 |
| --- | --- | --- |
| 안전·승인·권한·실패 보고 공통 계약 | root AGENTS.md | 모델/작업 종류와 관계없이 인지해야 하는 경계 |
| 특정 경로의 불변조건·관례 | 필요한 하위 AGENTS.md | 그 경로 작업 대부분에 필요한 고유 규칙; 패키지마다 기계적으로 만들지 않음 |
| 버그 분석·리팩터링·요구사항 등 절차 | 작업 Skill | 경로와 무관하게 작업 목적에 따라 선택 |
| 긴 설명·예외·예시·도메인 상세 | reference/기존 도메인 문서 | 상세가 필요한 조건과 진입점을 연결 |
| 이번 요청의 실행 계약 | TASK 및 작업별 계획 | 목표·인수 조건·허용 파일·핵심 근거·검증·중단/재분석 조건 |
| 모델별 추가 안내 | 필요성이 입증된 작은 선택 문서 | 공통 정책 복제 금지; 실제 실패 근거가 있는 행동 차이만 포함 |

같은 규칙의 소유 위치를 하나로 정하고 다른 진입점은 참조한다. 루트 시작에서 하위 경로를 다룰 때의 명시적 읽기, 복수 경로 및 아직 경로가 없는 분석 작업을 모두 설계한다. cd나 파일 존재만으로 자동 로딩을 가정하지 않는다.
작업별 필수 검증은 최초 계약에 정하고 결과를 공유한다. 새 수정·실패·미해결 위험 없이 각 역할이 같은 전체 검사를 반복하게 만들지 않는다.

## 4. After-v1 목적과 고정할 실행 조건

[PR #224의 Before/After 논의](https://github.com/dnd-side-project/dnd-15th-2-backend/pull/224#issuecomment-5645712660)에 따라 개선 지침은 이후 두 사용자가 실사용할 After의 1차 기준 후보로 준비한다. 사람이 선택하는 모델, 계획/실행 방식, 작업 순서를 하나의 권장 워크플로우로 강제하지 않는다.

이번 제한 검증에서는 Sol/high의 한 작업 세션이 요청을 수행하고 별도 세션이 동일 기준으로 결과를 검토하는 구성을 양쪽에 동일하게 적용한다. 모델/effort, 세션 분리 방식, 사용자 응답, 도구·권한, 검사와 중단 조건을 고정하고 지침 구성만 변경한다. 실제 호출 전에 fixture의 역할·승인 계약과 이 실행 구성이 호환되는지 확인한다.

고정하는 것은 실행 방식이며 과제 종류가 아니다. 기능·버그·리팩터링·설계·요구사항·복합 작업을 유지해 테스트/인프라에만 근거가 치우치지 않도록 한다. Astra 계획→Sol 구현과 Sol 단독의 비교, 모델별 비용 순위, 최적 라우팅 선정은 수행하지 않는다.

제한 검증은 같은 조건에서 지침 변경 전후의 차이를 확인한다. 이후 기간 실측에서는 사용자별 실제 워크플로우를 허용하고 작업 유형·난이도·모델·하네스 버전을 함께 기록한다. 그 기간의 단순 총량 차이를 지침만의 인과 효과로 단정하지 않는다. 측정 플랫폼 구축은 별도 작업이다.

### 단계 3: 고정 워크플로우에서 지침 변경 전후 비교

C0와 C1을 같은 Sol/high로 실행한다. 안전·인수 조건·검증 명령·권한·작업 내용은 동일하게 유지한다. 내용과 배치를 함께 바꿨다면 결과를 순수 배치 효과가 아닌 지침 구성 묶음의 효과로 보고한다.

- pilot: 별도 소형 fixture로 C0/C1 각1세션, 독립 gate 검토1세션. 본 비교에서 제외한다.
- 본 비교: F/B/R/A/Q/X 각1회 ×2구성 =12개 작업 실행 세션.
- 독립 결과 검토: 고정 Sol/high2세션이 각각6산출물을 검토한다. 각 과제 쌍은 같은 검토자가 보되 후보명/모델을 가리고 순서를 교차한다. 정량 인수검사는 동일 스크립트로 판정한다.
- 실행 순서는 F:C0→C1,B:C1→C0,R:C0→C1,A:C1→C0,Q:C0→C1,X:C1→C0로 고정한다.
- 신규 평가/평가검토 세션 합계17회. parent가 모델을 추가 호출하거나 하위 세션을 자동 생성하는 것은 허용하지 않는다.

n=1 탐색으로 전체 효율 우열·유의성·모델 일반화를 주장하지 않는다. 품질 실패를 제외한 비용만 보여주지 않고 실패율·소모량을 함께 기록한다. C1의 효과가 혼재하면 영역별 수정/보류를 결정한다.

### 단계 4: After-v1 후보 판단과 기간 실측 연결

- [ ] 동일 과제의 기존/개선 지침에 대해 품질과 입력·캐시·출력 토큰의 차이 및 절감률을 보고한다.
- [ ] 결과가 엇갈리는 부분의 규칙·배치를 수정 또는 보류한다. 결과를 보고 과제를 바꿔 재평가하면 별도 batch로 기록한다.
- [ ] 반복 검증이 필요하면 대상·횟수·예산을 새로 제시한다. 제안된17세션에 자동 추가하지 않는다.
- [ ] 제한 검증을 통과한 구성은 After-v1 후보로 제시한다. 작은 표본으로 모든 사용자/모델에서의 개선을 주장하지 않는다.
- [ ] 실제 Before의 버전과 After-v1의 최종 commit을 고정해 두 사용자의 기간 측정에 연결한다. 실제 작업 비중을 모르면 가중 전체 평균을 임의로 만들지 않는다.

## 6. 측정과 판정

주 지표: 동일한 인수 조건을 충족한 작업의 전체 입력·출력 토큰 변화. 캐시 입력은 전체 입력의 부분집합으로 별도 표기하고 중복 합산하지 않는다. 비캐시 입력도 분리한다. 절감률은 각 지표에 대해 (기존값−개선값)/기존값×100으로 계산하며 기존값이0이면 계산 불가로 표기한다.
품질은 선행 조건이다. 미완료·품질 저하로 적게 사용한 토큰을 최적화 성공으로 판정하지 않는다. 실패 실행의 소모와 전체 성공률도 함께 보고한다. 6개 과제별 수치가 기본이며 합계 절감률은 이 고정 과제 묶음에 한정한다.
API 환산 비용과 시간은 참고 지표이며 워크플로우의 비용 우열을 선정하는 데 사용하지 않는다. 계획·구현·수정·독립 평가 검토의 사용량을 가능한 범위에서 분리하고 전체 실험 사용량에는 모두 포함한다.
모든 비교군에 동일한 독립 평가 비용을 적용하되, 여러 결과를 한 세션에서 검토한 비용은 특정 산출물에 정확 귀속하지 않고 batch 검토 비용으로 보고한다.
보조 지표: 첫 시도 성공률, 인수 조건 충족, 유효한 질문/불필요한 재질문, 같은 hash 문서 재읽기, 광범위 탐색, 반복 검사, 모델 전환/재시도/compaction.
지침 지표: startup chain/file bytes, 관측된 추가 읽기, Skill metadata, 정확 귀속 가능한 tokens. 미확보값은 UNAVAILABLE;전체 입력을 instruction 토큰으로 치환하지 않는다.
API 환산액은 실제 Codex 구독 청구액·한도 소모율과 다르다. 계정 공유 한도는 다른 작업의 영향을 받으므로 API 토큰만으로 모델별 한도 절감률을 추정하지 않는다.
